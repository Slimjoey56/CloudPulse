# Robust Z-Score Baseline — Initial Results

## Run provenance

Results were generated by GitHub Actions from the pinned Microsoft Cloud Monitoring Dataset commit `6a07a53c2fac495fb6831811df4c980d6c04bd10`. The experiment used the prepared modelling view and per-series chronological 60/20/20 train/validation/test partitions. The detector threshold was fixed at 3.5 before evaluation; it was not tuned on validation or test labels.

## Test-set coverage

| Measure | Observed |
|---|---:|
| Test rows | 45,051 |
| Scored rows | 38,175 |
| Unscored rows due to zero-variance training series | 6,874 |

| Positive labels in unscored rows | 49 |

Five series had zero MAD and zero IQR in their training partition. They were marked unscorable rather than assigning arbitrary anomaly flags to every deviation. The 49 positive labels in those series are reported separately.

## Validation-selected threshold comparison

A second experiment selected a threshold independently for each series by maximising validation F1 over the predeclared grid. The test labels were not used to choose thresholds. Series with no positive validation labels or an unscorable training scale retained the fixed threshold of 3.5.

| Test metric | Fixed 3.5 threshold | Validation-selected threshold |
|---|---:|---:|
| True positives | 319 | 335 |
| False positives | 2,594 | 2,572 |
| False negatives | 208 | 192 |
| Precision | 10.95% | 11.52% |
| Recall on scored rows | 60.53% | 63.57% |
| F1 on scored rows | 18.55% | 19.51% |
| Recall counting unscored positives as misses | 55.38% | 58.16% |
| F1 counting unscored positives as misses | 18.29% | 19.24% |

Of the 60 series, 19 received a threshold selected on validation, 36 fell back because validation had no positive labels, and five were unscorable because their training scale was zero. The improvement is modest, and precision remains low.

## Interpretation

The baseline detects some labelled anomalies but produces a large number of false positives. A precision of 10.95% means most flagged scored observations are not labelled anomalies in this test partition. It is not suitable for operational alerting in its current form.

The conservative recall calculation counts the 49 unscored positive labels as missed, rather than silently removing them from the recall denominator. Per-series results are retained in the JSON artifact because the pooled micro metrics hide substantial variation between metrics.

## What this result establishes

- The data preparation, chronological split, training-only robust statistics, fixed-threshold scoring, and point-label evaluation pipeline runs end-to-end on the pinned dataset.
- A simple robust z-score is a reproducible baseline for later comparison.
- The false-positive burden and unscorable series are measurable limitations that subsequent methods must address.

## What it does not establish

- It does not demonstrate production-grade anomaly detection.
- It does not establish event-level detection performance.
- It does not validate CPU/memory prediction, root-cause analysis, capacity forecasting, or generalisation to other cloud providers.
- It does not justify tuning a threshold on the held-out test partition.

The full per-series validation and test metrics are available in the `microsoft-cloud-monitoring-baseline` GitHub Actions artifact.
